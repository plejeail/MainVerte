# Generation and activation

Follow the affected part of this chain:

`app_qt/CMakeLists.txt` → `tools/translate.cmake` → `tools/generate_translations.py` → build-tree `app_qt/generated/generated_translations.hpp` → `app_qt/src/translator.*` → QML callers.

- Generation uses a host Python interpreter, including Android builds. CMake tracks dictionaries and the generator through a stamp and generated byproduct; unchanged header content is not rewritten. Preserve incremental-build behavior when changing this pipeline.
- The header exposes language catalogs and `TextId` through Qt metatype/QML registration. Retain AUTOMOC/type registration when changing consumers; merely including a generated enum is not enough to expose it to QML.
- `ts::select_initial_language()` chooses a saved valid language before system preferences and fallback. Inspect its current behavior before changing precedence or language-code handling.
- `Ts::get()` marks a QML translation binding. The application connects the settings/wizard language signal to the relevant engine's `retranslate()`. A changed catalog selection alone does not refresh existing bindings; C++ consumers also need their own update path where relevant.
- `AppSettings` persists selection through Core asynchronously; the wizard has its own selection flow. Preserve the actual pending/error behavior rather than treating language activation as proof of a successful save.

Run `python -B tools/tests/test_generate_translations.py` for generator changes. Generate into a build/temporary directory, never source directories. Use `app_qt/tests/test_setup_language.cpp` for selection, persistence and immediate QML retranslation coverage; extend only the relevant cases. Check startup and runtime activation separately when both are affected.
